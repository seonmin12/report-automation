# 벤치마크 결과 요약

MVNO 실적 검증 파이프라인이 얼마나 큰 데이터까지 처리할 수 있고, 어디를 최적화하면
효과가 있는지 100% 합성 데이터로 측정했다. 실제 사내 데이터는 전혀 사용하지 않았다.

재현 방법:
```bash
python benchmark/generate_dummy.py --rows 300000 --seed 42   # 더미데이터 + 정답 생성
python benchmark/run_benchmark.py                             # 단계별 시간/메모리 측정
python benchmark/check_accuracy.py                             # 탐지 누락/오탐 측정
python benchmark/run_optimizations.py                          # dtype/usecols/merge 최적화 전후 비교
python benchmark/run_chunk_experiment.py                       # 청크 처리 실험 (별도)
```

## 1. 행 수별 처리 시간 / 피크 메모리 (최적화 전, 베이스라인)

| 행 수 | 파일로드 | merge | 검증 | 리포트생성 | 총합 | RSS 피크 |
|---|---|---|---|---|---|---|
| 10,000 | 0.05s | 0.07s | 0.01s | 0.38s | 0.51s | 140MB |
| 50,000 | 0.11s | 0.13s | 0.02s | 0.44s | 0.70s | 182MB |
| 100,000 | 0.22s | 0.20s | 0.04s | 0.58s | 1.04s | 214MB |
| 200,000 | 0.34s | 0.33s | 0.07s | 0.72s | 1.45s | 297MB |
| 300,000 | 0.49s | 0.51s | 0.10s | 0.88s | 1.98s | 354MB |

측정 방식: 각 규모를 독립된 파이썬 프로세스에서 실행해 `resource.getrusage`(RSS)와
`tracemalloc`(Python 레벨 피크)을 같이 측정. RSS를 실제 메모리 사용량 기준으로 삼았다
(tracemalloc은 numpy/pandas의 C 레벨 버퍼 일부를 못 잡을 수 있어서 저평가될 수 있음).

"리포트생성"이 항상 전체의 60~70%로 제일 오래 걸리는데, 세부 내역을 보면
`build_summary_image`(matplotlib)가 행 수와 무관하게 거의 고정 비용(0.28~0.31초 —
사업자 8곳짜리 표 이미지라서)이고, `build_excel_report`만 행 수에 비례해서 늘어난다
(0.08s → 0.55s).

**10,000~300,000행 전 구간에서 실패(예외/타임아웃)한 규모는 없었다.**

## 2. 서버리스 실행 한도 내에서 처리 가능한 최대 행 수

Vercel Functions 공식 문서 기준([vercel.com/docs/functions/limitations](https://vercel.com/docs/functions/limitations),
2026-07-01 갱신) Hobby(무료) 플랜 한도:

| 항목 | Hobby 플랜 |
|---|---|
| 메모리 | 2GB (기본값=최대값) |
| 최대 실행시간 | 300초 (기본값=최대값) |
| **요청 바디(업로드) 크기** | **4.5MB** |

**결론: 이 파이프라인의 실제 병목은 컴퓨팅이 아니라 요청 바디 크기다.**

- 컴퓨팅 한도(300초/2GB)는 1번 표의 증가 추세로 단순 선형 외삽하면 각각 약 5,900만 행,
  약 258만 행 부근에서나 걸릴 것으로 추정된다 (⚠️ 실측이 아니라 추정치 — 이 프로젝트가
  다루는 실제 규모(20만~30만)를 훨씬 초과하는 범위라 검증하지 않았다. [이유](#3-단계-없이-멈춘-이유)는 아래 참고).
- 반면 `POST /api/validate`는 포털/RAW/매핑 3개 파일을 multipart로 한 번에 올리는
  요청이라 **4.5MB 요청 바디 제한**이 걸린다. RAW CSV 실측 크기는 행당 **110.6바이트**
  (`benchmark/data/*/raw_transactions.csv` 5개 규모 전부 110.6~111.6바이트/행으로
  일정) — 이 기준으로 계산하면 **RAW 약 4만 2천~4만 3천 행 부근에서 413(요청 바디
  초과) 에러**가 난다. 실제로는 여기에 포털/매핑 파일까지 같은 요청에 얹히므로
  체감 한도는 이보다 조금 더 낮다.
- 즉 컴퓨팅 관점에서는 여유가 매우 크지만(수백만 행 단위), **웹 업로드 경로는
  4~5만 행 근처에서 이미 막힌다** — dtype/usecols 최적화로는 이 벽을 못 넘는다.
  더 큰 파일을 다루려면 아키텍처를 바꿔야 한다(예: 클라이언트에서 Object
  Storage로 직접 업로드 후 서버는 경로만 받기, 또는 CSV를 압축해서 전송).

### 3단계 이상 없이 멈춘 이유

원래 계획엔 "터지는 지점을 기록"이 있었지만, 20만(실제 월말 규모)~30만(여유분)
구간에서 실패가 하나도 없었고, 이 프로젝트가 다룰 일 없는 수백만 행까지 억지로
올려서 breaking point를 찾는 것은 실무적 의미가 없다고 판단해 생략했다 (사용자
논의 후 결정). 대신 위 표처럼 **실제 규모의 1.5배까지 여유 있게 확인**하고,
**진짜 병목이 컴퓨팅이 아니라 요청 크기라는 걸 밝히는 쪽**으로 방향을 잡았다.

## 3. 검증 정확도 (탐지 누락 / 오탐)

accuracy(정확도) 지표는 안 썼다 — 정상 데이터가 압도적으로 많아 의미가 없어서다.
대신 절대 건수로 본다: **탐지 누락**(주입했는데 못 잡음) / **오탐**(정상인데
오류로 잡음, 실무상 더 치명적).

| 행 수 | 매핑누락 | 중복 | 비활성사용 | 명칭불일치 | 실적비교 | 누락 합계 | 오탐 합계 |
|---|---|---|---|---|---|---|---|
| 10,000 | 4/4 | 3/3 | 6/6 | 4/4 | 11/11 | 0 | 0 |
| 50,000 | 10/10 | 6/6 | 12/12 | 8/8 | 20/20 | 0 | 0 |
| 100,000 | 20/20 | 12/12 | 25/25 | 16/16 | 40/40 | 0 | 0 |
| 200,000 | 40/40 | 25/25 | 50/50 | 33/33 | 80/80 | 0 | 0 |
| 300,000 | 60/60 | 37/37 | 75/75 | 50/50 | 120/120 | 0 | 0 |

(표 형식: 탐지/정답). **5개 규모 × 5개 오류 유형 전부 누락 0건, 오탐 0건** — 지금
코드(최적화 전) 기준으로 완벽하게 정확하고, 이게 아래 최적화 전후 비교의
베이스라인이다.

## 4. 최적화 before/after 비교

기존 소스(`src/`, `main.py`, `web/app.py`)는 건드리지 않고, `benchmark/optimized.py`에
같은 로직을 재현해서 실험했다 (실제 앱에 반영하려면 별도 작업 필요).

### 4-1. dtype 지정 → usecols → merge 키 dtype 정합 (누적 적용)

| 행 수 | 레벨0(베이스라인) | 레벨1(+dtype) | 레벨2(+usecols) | 레벨3(+merge정합) | 총합 시간 개선 | RSS 메모리 절감 |
|---|---|---|---|---|---|---|
| 10,000 | 0.53s / 139MB | 0.52s / 142MB | 0.56s / 139MB | 0.59s / 142MB | -11.5%(노이즈) | -2.1%(노이즈) |
| 50,000 | 0.77s / 181MB | 0.76s / 173MB | 0.87s / 164MB | 0.74s / 164MB | 3.0% | 9.2% |
| 100,000 | 1.08s / 227MB | 1.04s / 217MB | 1.03s / 194MB | 0.97s / 190MB | 9.8% | 16.3% |
| 200,000 | 1.52s / 296MB | 1.50s / 287MB | 1.41s / 241MB | 1.41s / 226MB | 7.8% | 23.5% |
| 300,000 | 1.99s / 356MB | 2.03s / 324MB | 1.79s / 292MB | 1.82s / 290MB | 8.9% | 18.4% |

**메모리 절감이 시간 단축보다 뚜렷하고 일관적이다** (규모가 클수록 9%→16%→24%→18%로
꾸준히 절감). 시간은 10,000행처럼 작은 규모에서 서브프로세스 기동 오버헤드에
묻혀 노이즈가 크고, 100,000행 이상에서야 8~10% 단축이 안정적으로 보인다.

**개별 기여도** (직접 원인 확인):
- **dtype 지정**: 메모리 절감의 핵심. RAW 컬럼 대부분을 `category`로 바꾸는 것만으로
  50,000행 이상에서 메모리가 눈에 띄게 줄었다.
- **usecols**: 코드를 다시 읽으면서 발견한 것 — RAW의 `선후불구분`/`채널`/`등록시각`,
  매핑표의 `요금제유형`/`비고`가 검증 파이프라인 어디서도 안 쓰였다. 이 5개 컬럼을
  안 읽는 것만으로 파일로드 시간이 눈에 띄게 줄었다(예: 300,000행 로드 0.52s→0.39s).
- **merge 키 dtype 정합**: 효과가 제일 작고 규모에 따라 들쭉날쭉했다 — portal_df와
  raw_agg_df가 원래도 같은 컬럼명·유사한 값 범위를 쓰고 있어서, 정합을 맞춰도
  pandas가 이미 빠른 경로를 타고 있었던 것으로 보인다.

**dtype 최적화 도중 발견한 버그 (그리고 왜 정확도 재확인이 중요한지)**: 상품명
컬럼을 category로 바꿨다가 `check_name_mismatch()`가
`TypeError: unhashable type: 'list'`로 죽었다. 이 함수가
`.groupby(...).agg(lambda s: sorted(set(s)))`로 그룹별 "이름 리스트"를 만드는데,
원본 컬럼이 category면 pandas가 결과(list)를 다시 category로 캐스팅하려다
실패하는 것. 상품명을 category에서 뺴서 해결했다 — **"동작을 바꾸지 마"라는
원칙이 실제로 걸린 사례**라 기록해 둔다.

### 4-2. 정확도 재확인 (최적화 전후 탐지 결과가 같은가)

레벨 0~3 × 5개 규모, 총 20번의 실행 **전부 누락 0건, 오탐 0건** — 최적화가 검증
로직의 동작을 바꾸지 않았음을 확인했다.

## 5. 청크 처리 적용 가능/불가능 검증의 구분과 이유

0단계에서 분류한 기준(행 단위로 독립 판정 가능한가) 그대로:

| 검증 | 청크 처리 | 이유 |
|---|---|---|
| 매핑누락 | ✅ 적용 | 매핑표에서 만든 코드 집합(작음)만 미리 구하면, RAW 각 행은 독립적으로 그 집합에 속하는지만 봄 |
| 비활성사용 | ✅ 적용 | 위와 동일 패턴 (비활성 코드 집합만 사전 계산) |
| 중복 매핑 | ❌ 제외 | `mapping_df.duplicated()`는 매핑표 전체를 봐야 하는 전역 연산 (다만 매핑표 자체가 작아서 원래도 문제없음) |
| 명칭불일치 | ❌ 제외 | `raw_df.groupby(상품코드)[상품명].agg(set)`으로 RAW 전체를 훑어야 코드별 이름 변형을 모을 수 있음 |
| 실적비교 | ❌ 제외 | RAW를 먼저 전체 groupby로 집계해야 하는 구조 (다만 count 합산이라 map-reduce로는 안전하게 나눌 수 있음 — 이번 실험 범위 밖) |

청크 처리는 매핑누락·비활성사용 두 검증에만 적용해서, RAW CSV를 파일에서
`chunksize` 단위로 스트리밍하며 결과를 누적하는 방식으로 구현했다
(`benchmark/chunked_check.py`). 원본 함수와 완전히 동일한 결과가 나오는지
DataFrame 단위로 직접 대조했고, 5개 규모 전부 일치했다.

| 행 수 | 원본(전체 로드 후 검사) | 청크 스트리밍 | RSS 절감 |
|---|---|---|---|
| 10,000 | 0.163s / 98MB | 0.025s / 99MB | -0.8%(노이즈) |
| 50,000 | 0.219s / 129MB | 0.105s / 153MB | -18.3%(노이즈) |
| 100,000 | 0.293s / 161MB | 0.181s / 151MB | 5.9% |
| 200,000 | 0.420s / 197MB | 0.368s / 182MB | 7.9% |
| 300,000 | 0.583s / 243MB | 0.563s / 189MB | 22.4% |

**중요한 단서**: 이 표는 매핑누락+비활성사용 **두 검증만 떼어낸** 결과다. 이
프로젝트의 실제 파이프라인에서는 명칭불일치 검증과 집계 단계가 어차피 RAW
전체를 메모리에 올려야 해서, 청크 처리를 붙여도 **전체 파이프라인의 피크
메모리는 줄지 않는다.** 청크 처리는 "이 두 검증만 먼저 빠르게 훑어야 하는
상황"이나 "RAW 파일이 메모리에 통째로 못 올라갈 만큼 훨씬 큰 경우"에나 의미가
있다 — 지금 이 프로젝트 규모(최대 30만 행, 350MB)에서는 해당하지 않는다. 이건
"청크 처리를 무조건 적용"이 아니라 "언제 의미 있는지 판단"한 결과로 남겨둔다.

## 정리

- 10,000~300,000행 전 구간에서 실패 없음 (컴퓨팅은 이 프로젝트 규모에서 병목이 아님)
- **실제 병목은 Vercel 요청 바디 4.5MB 제한 — RAW 약 4만 2천~4만 3천 행 부근**
- 검증 정확도: 5개 규모 × 5개 유형, 누락 0건·오탐 0건 (최적화 전/후 모두)
- dtype+usecols로 메모리 최대 24% 절감, 시간 최대 10% 단축 (100,000행 이상에서 안정적)
- 청크 처리는 조건부로만 의미 있음 — 무조건 좋은 최적화가 아니라는 것도 결과로 확인
